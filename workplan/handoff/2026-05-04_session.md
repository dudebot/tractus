## Validation playbook (for the next creator session)

When the user reactivates this session at a phase boundary
("phase X just closed"), the workflow is:

1. Read INDEX.md status table to see what claims to be `done`.
2. For each `done` task in the phase, run the task file's
   "Acceptance gates" section as a checklist:
   - Did the runbook produce a JSON report at the expected path?
   - Are the gate thresholds met?
   - Are there `flagged_*.jsonl` files needing review?
3. **Spawn Codex** (`mcp__codex__codex`) with a focused brief on
   what landed. Cold-thread review, since Codex is sharper as a
   reviewer than as a self-reviewer of its own prior outputs.
   Brief format: paste the task file + the JSON report + ask
   "what corners did the worker cut?"
4. **Spawn Explore** subagents on the actual code/test changes for
   regression smell. Look for:
   - Cheat-channel violations (free `wall_*` or
     `frication_gates` per-frame outputs).
   - fp64 silently re-enabled.
   - Surrogate imports in inference paths.
   - Aggregate-only reporting (no per-axis breakdown).
   - Knot-grid kinematic caps (must be continuous-time grid).
5. Compose a one-page validator-report at
   `handoff/<DATE>_phase-X-validation.md` with:
   - Per-task pass/fail.
   - Codex findings.
   - Subagent findings.
   - Recommended next move.
6. If all clear: mark phase closed in INDEX.md, advance status
   table, release downstream tasks.
7. If not clear: file follow-up tasks (`tasks/<phase>/00N+1_*.md`)
   for the gaps.

User involvement is for **decision-point tasks** only (listed in
INDEX.md "Decision points"). Validation itself is automated by the
runbooks; the validator session is the meta-reviewer.
